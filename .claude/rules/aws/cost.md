# 検証の進め方 (動かす時間を短くする)

時間課金のリソースは、検証するときだけ動かし、動かしている時間をできるだけ短くする。
`enable_runtime` の仕組みと料金は、`CLAUDE.md` の「費用を止める運用」と `docs/infra/runtime.ja.md` を参照する。

## 止めたまま準備する

- 実装、静的検査 (`just infra::check`、`just backend::check`)、plan の確認は、`enable_runtime = false` のまま済ませる
- **動かす前に、Notion の「検証用」DB に、確かめることごとにページを作り、次を整理する。** 1 ページでは 1 つのことだけを確かめる。1 回の起動で、複数のページを進めてよい。ユーザーが内容を確かめてから、`true` で apply してもらう
  - プロパティ: `検証内容` (タイトル)、`ID` (連番)、`ステータス` (未着手 / 進行中 / 完了)
  - 調べたいこと・確かめたいこと
  - 実行するコマンド (状態の確認、ログの取得、k6 など)
  - 取る出力 (PR の動作確認に貼る分を含む)
- DB: [検証用](https://app.notion.com/p/41fc6ef1bc098008b559e0b2cdd7ecfd) (`collection://41fc6ef1-bc09-80cd-b997-000b02a803b6`)

## 動かしたら一気に取る

- ユーザーが `enable_runtime = true` で apply したら、一覧の確認と、ログ・出力の取得をまとめて行う
- 出力はその場で控える (PR の `<details>` に貼る分を含む)。止めるとリソースが消え、サービスのイベントやターゲットのヘルスは取り直せない
- 想定外の結果が出たら、原因を調べるのに要るログと状態を先に取り切る。調査やコードの修正に時間がかかりそうなら、一度止めることを提案する

### ログのファイルの置き場所

> [!IMPORTANT]
> **検証で取るログや出力のファイル (`tee` の書き出し先など) を、リポジトリの直下に出さない。** 直下に置くと、Git の対象のファイルと紛れ、誤ってコミットされるおそれがある。

- Git の対象外の `tmp/` の下の、`logs/` に出す。`logs/` の下は、役割ごとのディレクトリに分ける
  - 例: k6 の検証なら `tmp/k6/logs/run/` (k6 の出力) と `tmp/k6/logs/target-health/` (ターゲットのヘルスの記録)
  - ディレクトリの名前は役割にする。時刻は入れない。親のディレクトリと同じ名前 (`tmp/k6/logs/k6/` など) は、冗長なので使わない
- ファイルの名前は、始めた時刻 (JST) にする (例: `20261128-173000.log`)。流し直しても、前の結果を上書きしない
- 途中で止めた回など、結果に使わないログは残さずに消す (`rm -f`)
- Notion の検証用のページに書くコマンドも、この置き場所に出す形で書く

## 終わったらすぐ止める

- 取り終えたら、次の作業に移る前に、`enable_runtime = false` にして apply するよう促す
- 作業を始めるときと、区切りをつけるときに、課金されるリソースが残っていないかを読み取りで確かめる (ECS のクラスター、ALB、インターフェース型エンドポイント)。残っていれば、ユーザーに伝える
- `enable_runtime = false` で apply したあとの確認は、`/cost-check` スキルで行う (別のエージェントが調べ、メインのセッションが検証してから報告する)
