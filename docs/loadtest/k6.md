# Load testing during deployments (k6)

[English](./k6.md) | [日本語](./k6.ja.md)

Back to the [documentation index](../README.md).

k6 checks that no request fails (no downtime) while a deployment runs under traffic.
k6 runs from your own PC. No AWS resources are created for load testing.

## How it works

- The script is `loadtest/scripts/deploy.js`. It keeps sending GET requests to `/` at a fixed RPS (`constant-arrival-rate`)
- k6 is not installed locally. It runs in a pinned container (`grafana/k6:2.4.0`), set by `k6_image` in `loadtest/justfile`
- **k6 exits with 99 if even one request fails** (a threshold is crossed). Requests that could not be sent at the planned RPS (`dropped_iterations`) also count as a failure

### Failure kinds

| Kind      | Condition                                            | Likely cause                                                 |
| --------- | ---------------------------------------------------- | ------------------------------------------------------------ |
| `timeout` | No response (10 seconds by default), connect timeout | The network, or something stuck behind the ALB               |
| `network` | DNS, TCP or TLS failure, connection closed           | The network (including connections closed during the switch) |
| `server`  | HTTP 5xx                                             | The ALB or the application. Compare with the ALB's 5xx count |
| `client`  | Any other non-200 response (4xx, ...)                | The target or routing configuration                          |
| `body`    | 200, but the version could not be read from the body | The application                                              |

If the ALB reports no 5xx but `timeout` or `network` appear, treat it as a problem with your own connection.
Each failure is logged (`level=warning`) with its kind, `status` and `error_code`.

### Counts per version

The script reads `{"version":"v1"}` from the body and counts it in `responses{version:<version>}`. Pass the versions to count in `versions`. Any other version is counted as `unknown`.
With rolling updates, old and new versions mix part way through. With canary and linear, the ratio changes at each step.

## Running it

Run it only while the target is up. `prd` is up only while `enable_runtime = true` ([Stopping and restarting the environment](../infra/runtime.md)).
A short network drop or the PC going to sleep also counts as a failure, so use a wired connection and keep the PC awake.

```sh
# Arguments: rate (requests per second), duration, versions, base_url. Defaults: 10 RPS for 5 minutes
just loadtest::run 20 10m v1,v2

# While it runs, push the v2 tag from another terminal to deploy
```

Pass a `duration` longer than the deployment takes.

### Output at the end

The `THRESHOLDS` and `CUSTOM` sections of the summary show the count per failure kind and per version.

```text
    CUSTOM
    failures.......................: 0     0/s
      { kind:body }................: 0     0/s
      { kind:client }..............: 0     0/s
      { kind:network }.............: 0     0/s
      { kind:server }..............: 0     0/s

```

## Trying it against a local container

You can check how the script behaves without running anything on AWS.

```sh
just backend::build v1
just backend::run v1   # keep it running in another terminal

# Send from k6 in its container to port 8080 on your machine
just loadtest::run 20 15s v1,v2 http://host.docker.internal:8080
```

Stopping the container part way through shows `network` failures being counted and k6 exiting with 99.

After changing the script, `just loadtest::inspect` shows the resulting options (scenario and thresholds). It sends no requests.
