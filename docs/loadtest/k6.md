# Load testing during deployments (k6)

[English](./k6.md) | [日本語](./k6.ja.md)

Back to the [documentation index](../README.md).

k6 checks that no request fails (no downtime) while a deployment runs under traffic.
k6 runs from your own PC. No AWS resources are created for load testing.

## How it works

- The entry point is `loadtest/scripts/availability.js`. It keeps sending GET requests to `/` at a fixed RPS (`constant-arrival-rate`)
- The test that drops a required field from the checkout API uses a separate entry point, `loadtest/scripts/checkout.js` ([Old and new checkout clients](#old-and-new-checkout-clients-checkoutjs))
- k6 is not installed locally. It runs in a pinned container (`grafana/k6:2.4.0`, pinned by digest), set by the `FROM` line of `loadtest/Dockerfile`, which `k6_image` in `loadtest/justfile` reads
- `just loadtest::run` and `just loadtest::inspect` pass the values (`BASE_URL`, `RATE`, `DURATION`) with k6's `-e`. Container environment variables (`docker run -e`) are not used, because `k6 inspect` does not read them
- **k6 exits with 99 if even one request fails** (a threshold is crossed). Requests that could not be sent at the planned RPS (`dropped_iterations`) also count as a failure
- Before the test starts (`setup()`), the script sends one request to `/` and remembers the running version as the old version. If the request fails or the version cannot be read, the test stops without starting and k6 exits with 108 (`exec.test.abort`)

### Files

The entry point holds only the load shape (scenario and thresholds). The logic lives in `loadtest/scripts/lib/`, one role per file.

| File                 | Role                                                                                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `availability.js`    | Entry point. `options` (scenario and thresholds), `setup()` that reads the old version, and the function that sends one GET |
| `lib/config.js`      | Reads the passed values (`__ENV`) and holds the defaults                                                                    |
| `lib/failure.js`     | The failure kinds, and how a response (status, error code) maps to a kind                                                   |
| `lib/root.js`        | Sends `GET /` (used by both `setup()` and the iterations)                                                                   |
| `lib/version.js`     | Reads the version from the body and labels it `old` if it matches the old version, otherwise `new`                          |
| `lib/old-version.js` | Reads the old version in `setup()` and logs it. Stops the test if it cannot be read                                         |
| `lib/metrics.js`     | The Counters (`failures`, `responses`) and their thresholds                                                                 |
| `lib/count.js`       | Looks at one response and counts it per failure kind, or as the old or the new version                                      |

`checkout.js` shares `lib/config.js`, `lib/failure.js`, `lib/version.js`, `lib/old-version.js` and the `failures` Counter in `lib/metrics.js`, and adds these files.

| File                      | Role                                                                                                                                            |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `checkout.js`             | Entry point. `options` (two scenarios and thresholds), `setup()` that reads the old version, and one function per client that sends one request |
| `lib/checkout.js`         | Builds the checkout body and sends `POST /v1/carts/{cart_id}/checkout`                                                                          |
| `lib/checkout-metrics.js` | The Counter (`checkout_responses`) and the thresholds for `checkout.js`                                                                         |
| `lib/checkout-count.js`   | Counts one response per version and status, and counts failures per kind, except the expected 400                                               |

k6 pre-allocates twice the RPS in VUs (at least 10) and can add only 10 more during the run. Iterations that cannot start for lack of VUs show up in `dropped_iterations` and count as a failure.

### Failure kinds

| Kind      | Condition                                            | Likely cause                                                 |
| --------- | ---------------------------------------------------- | ------------------------------------------------------------ |
| `timeout` | No response (10 seconds by default), connect timeout | The network, or something stuck behind the ALB               |
| `network` | DNS, TCP or TLS failure, connection closed           | The network (including connections closed during the switch) |
| `server`  | HTTP 5xx                                             | The ALB or the application. Compare with the ALB's 5xx count |
| `client`  | Any other non-200 response (4xx, ...)                | The target or routing configuration                          |
| `body`    | 200, but the version could not be read from the body | The application                                              |

If the ALB reports no 5xx but `timeout` or `network` appear, treat it as a problem with your own connection.
Each failure is logged (`level=warning`) with its kind, `status` and `error_code`.

### Counts per old and new version

The script reads `{"version":"v1"}` from the body. If it matches the old version (the one running when the test started), it is counted in `responses{version:old}`; otherwise in `responses{version:new}`.
The old version is logged once before the test starts (`old version=v1`). The version numbers themselves are not counted.
With rolling updates, old and new versions mix part way through. With canary and linear, the ratio changes at each step.

## Running it

Run it only while the target is up. `prd` is up only while `enable_runtime = true` ([Stopping and restarting the environment](../infra/runtime.md)).
A short network drop or the PC going to sleep also counts as a failure, so use a wired connection and keep the PC awake.

The last argument, `target`, is the name of the destination: `local` (the default, `http://host.docker.internal:8080`) or `prd` (`https://ecs-lab.tamaco-blog.jp`).
**Add `prd` only when sending to `prd`.** Leaving it out sends to the local container. Any other name stops the recipe before k6 starts.

```sh
# Arguments: rate (requests per second), duration, target. Defaults: 10 RPS for 5 minutes, to local
just loadtest::run 20 10m prd

# While it runs, push the v2 tag from another terminal to deploy
```

Pass a `duration` longer than the deployment takes.

## Trying it against a local container

You can check how the script behaves without running anything on AWS.
`just loadtest::serve <old|new>` builds the app image with the version set to `old` or `new`, and runs it in the foreground on port 8080 on your machine (`Ctrl-C` stops it). It calls `build` and `run` from `backend`.

```sh
# Terminal 1: run the old version
just loadtest::serve old

# Terminal 2: send from k6 in its container to port 8080 on your machine (target defaults to local)
just loadtest::run 20 15s
```

To try a switch, stop terminal 1 with `Ctrl-C` part way through a run such as `just loadtest::run 20 30s`, then start the new version with `just loadtest::serve new`.
Both `old` and `new` get counts. The `network` failures while nothing is running are counted, and k6 exits with 99.
Running it while the container is stopped makes `setup()` stop the test before it starts, and k6 exits with 108.

After changing the script, `just loadtest::inspect` shows the resulting options (scenario and thresholds). It sends no requests.
On PRs, `ci-loadtest` runs `inspect` and a short `run` against the application inside the runner ([Checking the k6 scripts](../ci/loadtest.md)).

## Old and new checkout clients (`checkout.js`)

Run this while a rolling deployment ships a version of the checkout API (`POST /v1/carts/{cart_id}/checkout`) that no longer requires `unit_price`.
The counts show that the new client gets 400 when it hits the old version, while the old client gets 200 from both versions.

### Scenarios

| Scenario     | Sender                                | `items[]` in the body               |
| ------------ | ------------------------------------- | ----------------------------------- |
| `new_client` | The new client (function `newClient`) | `sku`, `quantity` (no `unit_price`) |
| `old_client` | The old client (function `oldClient`) | `sku`, `quantity`, `unit_price`     |

- Both use `constant-arrival-rate`. `RATE` is the RPS per scenario (twice `RATE` in total)
- Both scenarios start together, before the deployment (no `startTime`), because
  - it is close to reality: the web front end is updated first, so new clients hit the old version
  - it confirms that every 400 before the deployment came from the old version
  - the same run shows the 400s dropping to 0 after the switch to the new version
- `cart_id` is generated with `crypto.randomUUID()` for each request, and the URLs are grouped under one `name` tag (`checkout`)
- The old version is read in the same way as `availability.js` (`GET /` in `setup()`)

### Counting

Every response whose `version` can be read from the body is counted in `checkout_responses`, per scenario (the `scenario` tag, added by k6) × the version that handled it (`version`: `old` / `new`) × the status (`status`).
It is counted whether or not it is a failure. The summary shows 8 combinations: 2 scenarios × `old` / `new` × `200` / `400`.

### Failures

| Scenario     | Success                     | Expected failure (not a threshold failure)                                  | Failure                                                           |
| ------------ | --------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `old_client` | 200 with a readable version | None                                                                        | Anything else (same kinds as `availability.js`)                   |
| `new_client` | 200 with a readable version | 400 from the `old` version with `error` = `items[0].unit_price is required` | 400 from the new version, 400 with another `error`, anything else |

- The expected 400 is only counted in `checkout_responses{scenario:new_client,version:old,status:400}`, not in `failures`
- The new client's requests pass `http.expectedStatuses(200, 400)` as `responseCallback`, so the expected 400 does not raise `http_req_failed`
- On top of that, the thresholds keep `http_req_failed: rate==0` and zero `failures` (in total, per kind and per scenario). An unexpected 400 is counted in `failures{kind:client}`
- k6 exits with 0 if there are no failures, and with 99 if there is even one

### Running it

```sh
# Arguments: rate (RPS per scenario), duration, target. Defaults: 10 RPS each for 10 minutes, to local
just loadtest::checkout 10 10m prd

# Show the resulting options (two scenarios and thresholds). It sends no requests
just loadtest::inspect-checkout 10 10m
```

Against the local container (`just loadtest::serve old`), every new-client request gets 400 (`old`), every old-client request gets 200 (`old`), and k6 exits with 0.
The current `new` version still requires `unit_price`, so switching to `new` part way through counts the new client's 400s under `version:new`, and k6 exits with 99.
