# デプロイ中の負荷試験 (k6)

[English](./k6.md) | [日本語](./k6.ja.md)

[ドキュメント一覧](../README.ja.md)に戻る。

リクエストを流している間にデプロイしても、失敗するリクエストが 0 件 (ダウンタイムなし) であることを、k6 で確かめます。
k6 は手元の PC から実行します。負荷試験のための AWS のリソースは作りません。

## 仕組み

- スクリプトの入り口は `loadtest/scripts/availability.js` です。`/` に一定の RPS (`constant-arrival-rate`) で GET を送り続けます
- 注文の確定 API の必須の項目を外す検証には、別の入り口 `loadtest/scripts/checkout.js` を使います ([注文の確定の新旧のクライアント](#注文の確定の新旧のクライアント-checkoutjs))
- k6 は手元に入れず、版を固定したコンテナ (`grafana/k6:2.4.0`) で動かします。`loadtest/justfile` の `k6_image` で固定しています
- `just loadtest::run` と `just loadtest::inspect` は、値 (`BASE_URL`、`RATE`、`DURATION`) を k6 の `-e` で渡します。コンテナの環境変数 (`docker run -e`) は、`k6 inspect` が読まないため使いません
- **1 件でも失敗すると、k6 は 99 で終わります** (閾値の超過)。予定の RPS を送れなかった分 (`dropped_iterations`) も失敗として扱います
- 始める前 (`setup()`) に `/` を 1 回送り、そのとき動いている版を古い版として覚えます。送れない、または版を読めないときは、試験を始めずに 108 で止まります (`exec.test.abort`)

### ファイルの構成

入り口には負荷の形 (シナリオと閾値) だけを置き、処理は `loadtest/scripts/lib/` に役割ごとに分けています。

| ファイル             | 役割                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| `availability.js`    | 入り口。`options` (シナリオと閾値)、古い版を読む `setup()`、1 回の繰り返しで GET を 1 件送る関数 |
| `lib/config.js`      | 渡された値 (`__ENV`) の読み込みと既定値                                                          |
| `lib/failure.js`     | 失敗の種類の一覧と、応答 (ステータス、エラーコード) から種類への分け方                           |
| `lib/root.js`        | `GET /` を送る (`setup()` と繰り返しの両方で使う)                                                |
| `lib/version.js`     | 本文からバージョン番号を読み、古い版と同じなら `old`、違えば `new` に分ける                      |
| `lib/old-version.js` | `setup()` で古い版の番号を読み、ログに出す。読めなければ試験を止める                             |
| `lib/metrics.js`     | 件数を数える Counter (`failures`、`responses`) と、その閾値の組み立て                            |
| `lib/count.js`       | 応答 1 件を見て、失敗なら種類ごとに、成功なら古い版か新しい版かで数える                          |

`checkout.js` は、上の `lib/config.js`、`lib/failure.js`、`lib/version.js`、`lib/old-version.js` と、`lib/metrics.js` の `failures` を共有し、次のファイルを足して使います。

| ファイル                  | 役割                                                                                                |
| ------------------------- | --------------------------------------------------------------------------------------------------- |
| `checkout.js`             | 入り口。`options` (2 つのシナリオと閾値)、古い版を読む `setup()`、クライアントごとに 1 件を送る関数 |
| `lib/checkout.js`         | 注文の確定の本文を組み立て、`POST /v1/carts/{cart_id}/checkout` を送る                              |
| `lib/checkout-metrics.js` | Counter (`checkout_responses`) と、`checkout.js` の閾値の組み立て                                   |
| `lib/checkout-count.js`   | 応答 1 件を、版とステータスごとに数え、想定どおりの 400 を除いた失敗を種類ごとに数える              |

前もって作る VU は RPS の 2 倍 (最低 10) で、途中で足せるのは 10 だけです。足りずに送れなかった分は `dropped_iterations` に出て、失敗になります。

### 失敗の種類

| 種類      | 条件                                          | 原因の見当                                        |
| --------- | --------------------------------------------- | ------------------------------------------------- |
| `timeout` | 応答が来ない (既定 10 秒)、接続のタイムアウト | 回線側、または ALB の先で詰まっている             |
| `network` | DNS・TCP・TLS の失敗、接続の切断              | 回線側 (切り替えのときに接続が切られた場合も含む) |
| `server`  | HTTP 5xx                                      | ALB かアプリ側。ALB の 5xx の件数と突き合わせる   |
| `client`  | 200 以外のそのほかの応答 (4xx など)           | 送り先や経路の設定                                |
| `body`    | 200 だが、本文からバージョン番号を読めない    | アプリ側                                          |

ALB の 5xx が 0 件なのに `timeout` や `network` が出たときは、手元の回線の問題と判断します。
失敗した 1 件ごとに、種類と `status`・`error_code` をログ (`level=warning`) に出します。

### 新旧の版ごとの件数

本文の `{"version":"v1"}` を読み、古い版 (流し始めた時点の版) と同じ番号なら `responses{version:old}`、違う番号なら `responses{version:new}` に数えます。
古い版の番号は、始める前に 1 回だけログ (`old version=v1`) に出します。番号そのものは数えません。
ローリングでは途中から新旧が混ざり、カナリアやリニアでは段階ごとに割合が変わります。

## 実行する

送り先が動いている間だけ実行します。`prd` は `enable_runtime = true` の間だけ動きます ([検証環境の停止と再開](../infra/runtime.ja.md))。
回線の瞬断や PC のスリープでも失敗になるため、有線でつなぎ、実行中はスリープしないようにします。

最後の引数 `target` は送り先の名前で、`local` (既定。`http://host.docker.internal:8080`) か `prd` (`https://ecs-lab.tamaco-blog.jp`) を渡します。
**`prd` に送るときだけ `prd` を付けます。** 省くと手元のコンテナに送ります。ほかの名前を渡すと、k6 を動かす前に止まります。

```sh
# 引数は rate (1 秒あたりの件数)、duration、target の順。省略すると 10 RPS で 5 分、送り先は local
just loadtest::run 20 10m prd

# 流している間に、別の端末から v2 のタグを push してデプロイする
```

デプロイが終わるまでの時間より長い `duration` を渡します。

### 終わったときの出力

サマリーの `THRESHOLDS` と `CUSTOM` に、失敗の種類ごとの件数と、新旧の版ごとの件数が出ます。

```text
    CUSTOM
    failures.......................: 0     0/s
      { kind:body }................: 0     0/s
      { kind:client }..............: 0     0/s
      { kind:network }.............: 0     0/s

```

## 手元のコンテナで試す

AWS を動かさずに、スクリプトの動きを確かめられます。
`just loadtest::serve <old|new>` は、版の値を `old` か `new` にしてアプリのイメージをビルドし、手元の 8080 番で前面で動かします (`Ctrl-C` で止まる)。ビルドと起動は `backend` の `build` と `run` を呼びます。

```sh
# 端末 1: 古い版を動かす
just loadtest::serve old

# 端末 2: コンテナの中の k6 から、手元の 8080 番に送る (target を省くと local)
just loadtest::run 20 15s
```

入れ替えを試すときは、`just loadtest::run 20 30s` などを流している途中で、端末 1 を `Ctrl-C` で止め、`just loadtest::serve new` で新しい版を動かします。
`old` と `new` の両方に件数が出ます。止めている間の `network` の失敗が数えられ、99 で終わります。
コンテナを止めたまま流すと、`setup()` で止まり、試験を始めずに 108 で終わります。

スクリプトを書き換えたときは、`just loadtest::inspect` で、組み立てた設定 (シナリオと閾値) を確かめられます。リクエストは送りません。
PR では、`ci-loadtest` が `inspect` と、runner の中のアプリへの短い `run` を流します ([k6 のスクリプトの検査](../ci/loadtest.ja.md))。

## 注文の確定の新旧のクライアント (`checkout.js`)

注文の確定 API (`POST /v1/carts/{cart_id}/checkout`) から必須の項目 (`unit_price`) を外した版を、ローリングで出す間に流します。
新しいクライアントが古い版に当たると 400 になり、古いクライアントはどちらの版でも 200 になることを、件数で示します。

### シナリオ

| シナリオ     | 送り手                                | 本文の `items[]`                      |
| ------------ | ------------------------------------- | ------------------------------------- |
| `new_client` | 新しいクライアント (関数 `newClient`) | `sku`、`quantity` (`unit_price` なし) |
| `old_client` | 古いクライアント (関数 `oldClient`)   | `sku`、`quantity`、`unit_price`       |

- どちらも `constant-arrival-rate` で、`RATE` はシナリオごとの RPS です (2 つ合わせて `RATE` の 2 倍)
- 2 つのシナリオは、デプロイの前から同時に流します (`startTime` は付けない)。理由は次のとおりです
  - Web のフロントが先に新しくなり、新しいクライアントが古い版に当たる場面に近い
  - デプロイの前の 400 が、すべて古い版から返ったことを確かめられる
  - 新しい版に切り替わったあと、400 が 0 件になることも、同じ流れで見られる
- `cart_id` は毎回 `crypto.randomUUID()` で作り、URL は `name` タグ (`checkout`) で 1 つにまとめます
- 古い版の読み方 (`setup()` で `GET /`) は `availability.js` と同じです

### 数え方

本文の `version` を読めた応答を、`checkout_responses` に、シナリオ (`scenario` のタグ。k6 が自動で付ける) × 処理した版 (`version`: `old` / `new`) × ステータス (`status`) ごとに数えます。
失敗かどうかに関わらず数えます。サマリーに出すのは、2 シナリオ × `old` / `new` × `200` / `400` の 8 つです。

### 失敗の分け方

| シナリオ     | 成功             | 想定どおりの失敗 (閾値の失敗に入れない)                          | 失敗                                               |
| ------------ | ---------------- | ---------------------------------------------------------------- | -------------------------------------------------- |
| `old_client` | 200 で版を読める | なし                                                             | それ以外 (種類は `availability.js` と同じ)         |
| `new_client` | 200 で版を読める | 400 で、版が `old`、`error` が `items[0].unit_price is required` | 新しい版が返した 400、`error` が違う 400、そのほか |

- 想定どおりの 400 は、`checkout_responses{scenario:new_client,version:old,status:400}` に数えるだけで、`failures` には数えません
- 新しいクライアントのリクエストには、`http.expectedStatuses(200, 400)` を `responseCallback` に渡します。想定どおりの 400 で `http_req_failed` が上がらないようにするためです
- そのうえで `http_req_failed: rate==0` と、`failures` の 0 件 (全体、種類ごと、シナリオごと) を閾値に置きます。想定と違う 400 は `failures{kind:client}` に数えます
- 失敗が 0 件なら 0、1 件でもあれば 99 で終わります

### 流す

```sh
# 引数は rate (シナリオごとの RPS)、duration、target の順。省略すると 10 RPS ずつで 10 分、送り先は local
just loadtest::checkout 10 10m prd

# 組み立てた設定 (2 つのシナリオと閾値) を確かめる。リクエストは送らない
just loadtest::inspect-checkout 10 10m
```

手元のコンテナ (`just loadtest::serve old`) に流すと、新しいクライアントはすべて 400 (`old`)、古いクライアントはすべて 200 (`old`) になり、0 で終わります。
今の `new` の版も `unit_price` を必須にしているため、途中で `new` に入れ替えると、新しいクライアントへの 400 が `version:new` に数えられ、99 で終わります。
